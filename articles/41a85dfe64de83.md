ML Platform Engineer として、普段から Karpenter を運用しています。管理しているクラスタで Karpenter を更新するにあたり、v1.15.0 で何が変わるかを調べました。

リリースノートだけでは挙動の変化を判断しにくい箇所があったため、ソースコード（`kubernetes-sigs/karpenter` の `v1.14.3..v1.15.0`）の差分を読みました。内部の動作を含めて、更新前に確認した内容をまとめます。

# 前提条件・環境

- 対象は `sigs.k8s.io/karpenter` のコアリポジトリです。
- v1.14.3 から v1.15.0 までの差分は 103 コミット、252 ファイルです。
- 半分近くはテスト、RFC（`designs/`）、依存更新です。本記事では挙動に影響するものに絞ります。
- cloud provider（AWS Provider など）側の変更は読んでいません。

# 変更点の全体像

|分類|変更|影響度|
|--|--|--|
|Node Repair|repair が Disruption の Method になった（budget の reason は `Unhealthy`）|大|
|Node Repair|repair の action に reboot が追加された|中|
|Node Repair|`--legacy-node-repair` フラグを追加|中|
|Disruption|capacity が逼迫した NodePool 向けの terminate-first（Drift / Repair）|中|
|Feature Gate|`TerminateFirstDrift` / `TerminateFirstRepair` / `PodDeletionCostManagement` を追加|中|
|Disruption|`PodDeletionCostManagement` で Pod の削除優先度を Karpenter が書き込む|中|
|API|`consolidateAfter` が必須ではなくなり、デフォルトが `0s` になった|小|
|Scheduling|`--scheduler-config` で kube-scheduler の default topology spread を反映|中|
|Scheduling|InstanceType の volume attach 上限を考慮|低|
|Metrics|`reason` ラベルの小文字化など、breaking なメトリクス変更|中|
|Metrics|`karpenter_pods_disruption_initiated_total` などを追加|低|

:::message alert
このリリースには、メトリクスのラベル値が変わる breaking change が含まれます。ダッシュボードやアラートで `reason` や `consolidation_type` を条件にしている場合は、更新前に確認してください。
:::

# Feature Gate の整理

v1.15.0 では、feature gate の定義が `options.FeatureGate` 構造体にまとまりました（[#3376](https://github.com/kubernetes-sigs/karpenter/pull/3376)）。名前、デフォルト値、ステージ、説明が 1 か所にあり、ドキュメント生成にも使われます。

```go: pkg/operator/options/options.go
type FeatureGate struct {
	// Name is the gate's name in --feature-gates, e.g. "NodeRepair".
	Name string
	// Default is whether the gate is enabled when it isn't set.
	Default bool
	// Stage is the stability of the gated feature.
	Stage docs.Stage
	// Help is human-readable documentation for the gate: what enabling it does.
	Help string
}
```

v1.15.0 で定義されている gate は次の 9 つです。

|Gate|デフォルト|ステージ|v1.14.3 からの変更|
|--|--|--|--|
|`NodeRepair`|false|Alpha|挙動が大きく変わる（後述）|
|`ReservedCapacity`|true|Beta|変更なし|
|`SpotToSpotConsolidation`|false|Alpha|変更なし|
|`NodeOverlay`|false|Alpha|変更なし|
|`StaticCapacity`|false|Alpha|変更なし|
|`CapacityBuffer`|false|Alpha|変更なし|
|`TerminateFirstDrift`|false|Alpha|新規|
|`TerminateFirstRepair`|false|Alpha|新規（`NodeRepair` が必要）|
|`PodDeletionCostManagement`|false|Alpha|新規|

新しい gate はすべてデフォルトで無効です。更新するだけで、新機能が有効になることはありません。

`--feature-gates` のデフォルト値と help 文字列は、この定義から生成されるようになりました（`featureGatesDefault()` と `featureGatesHelp()`）。gate を追加するたびに、フラグの説明を手で直す必要がなくなります。

# Node Repair が Disruption の Method になった

v1.15.0 の中心的な変更です。`NodeRepair` gate を有効にしている環境では、特に影響があります。

## 旧実装と新実装

v1.14.3 までの repair は、`node.health` という独立した controller でした。Node の unhealthy な condition を見て、toleration を過ぎたら NodeClaim を削除します。

v1.15.0 では、repair が `disruption.Method` として実装されました（[#3311](https://github.com/kubernetes-sigs/karpenter/pull/3311)）。Disruption の Method 一覧は次の順になります。

```go: pkg/controllers/disruption/controller.go
methods := []Method{}
// Repair runs first: fixing a fault outranks any discretionary rebalance. Do not register the method while the
// feature gate is disabled, since candidate construction performs cluster-wide API and scheduling work.
// --legacy-node-repair runs the legacy node.health controller in place of this method.
if options.FromContext(ctx).FeatureGates.NodeRepair && !options.FromContext(ctx).LegacyNodeRepair {
	methods = append(methods, NewRepair(c))
}
return append(methods, []Method{
	NewEmptiness(c),
	NewStaticDrift(cluster, provisioner, cp, recorder),
	NewDrift(kubeClient, cluster, provisioner, recorder, clk),
	NewMultiNodeConsolidation(c),
	NewSingleNodeConsolidation(c),
}...)
```

順序は `Repair → Emptiness → StaticDrift → Drift → Multi → Single` です。障害の修復を、コスト最適化より優先します。

## 何が変わるか

`Repair` の実装（`pkg/controllers/disruption/repair.go`）から読み取れる挙動は、次のとおりです。

|項目|内容|
|--|--|
|budget|NodePool の `disruption.budgets[].reasons` に `Unhealthy` が追加された。repair の同時実行数は、他の Disruption と同じ budget で制御される|
|候補の順序|`rank + 経過時間 / 30 分` のスコアが高い順。同点なら disruption cost が低い順、さらに Node 名の順|
|置換用の容量|Pod が載っているノードは、再スケジュール先の容量を確認し、必要なら先に置換ノードを起動する（pre-spin）|
|遮断|annotation `karpenter.sh/do-not-repair: "true"` で repair を止められる。`do-not-disrupt` とは独立|
|ブレーカー|NodePool の 20% 超が unhealthy だと、その NodePool の repair を止める|
|blocking Pod|PDB や `do-not-disrupt` の Pod があるノードは、`terminationGracePeriod` がないと repair されない|
|1 回の処理|1 回の pass で出すコマンドは 1 つ（Drift と同じ）|

### スコアによる優先順位

スコアは `health/policy.go` の `ScoreAt` で計算されます。

```go: pkg/controllers/node/health/policy.go
// ScoreAt returns the result's repair score as of now: the highest rank + age/agingConstant across its eligible
// policies, where age is the time since the policy became eligible.
func (r RepairResult) ScoreAt(now time.Time) float64 {
	if r.Action == "" {
		return 0
	}
	return float64(r.scoreRank) + now.Sub(r.scoreEligibleAt).Minutes()/agingConstant.Minutes()
}
```

`rank` は cloud provider が返す `RepairPolicy` の priority から決まります。`agingConstant` は 30 分です。優先度の低い policy でも、待ち時間が長くなるほどスコアが上がるため、後回しにされ続けることはありません。

`ScoreAt` に渡す `now` は、全候補で同じ値です（[#3406](https://github.com/kubernetes-sigs/karpenter/pull/3406)）。評価順によって経過時間がずれ、順位が入れ替わるのを防いでいます。

### Initialize されないノードの repair

[#3393](https://github.com/kubernetes-sigs/karpenter/pull/3393) で、Node として登録されたのに Initialize されないノードも repair の対象になりました。toleration は、登録された時刻から数えます（[#3397](https://github.com/kubernetes-sigs/karpenter/pull/3397)）。

```go: pkg/controllers/disruption/repair.go
// Budgets only count initialized nodes, since an uninitialized node runs no workload to protect, so repairing one
// neither needs nor consumes budget.
if candidate.Initialized() && disruptionBudgetMapping[candidate.NodePool.Name] == 0 {
	continue
}
```

Initialize 前のノードには守るべき Pod がないため、budget を消費しません。budget を `0` にしていても、起動に失敗し続けるノードは repair されます。

### events

`do-not-repair` で止められた場合や、ブレーカーが働いた場合は、Node と NodeClaim に event が出ます（`DisruptionBlocked`、`NodeRepairBlocked`）。「repair されない」ときは、まず event を確認します。

## reboot が repair の action に追加された

[#3345](https://github.com/kubernetes-sigs/karpenter/pull/3345) と [#3377](https://github.com/kubernetes-sigs/karpenter/pull/3377) で、repair が「ノードを置換する」以外に「再起動する」ことを選べるようになりました。

どちらを使うかは、cloud provider が返す `RepairPolicy` の action（`ReplaceNode` / `RebootNode`）で決まります。AWS Provider がどの policy に reboot を割り当てるかは、この調査では確認していません。

### reboot controller

reboot は、`nodeclaim.reboot` という専用の controller が実行します。コミットした側（repair）は、NodeClaim に `Rebooting=True` の condition を `RebootRequested` という reason で付けるだけです。後は controller が drain、実行、観察を進め、`RebootSucceeded` か `RebootFailed` で終えます。

```go: pkg/apis/v1/nodeclaim_status.go
const (
	RebootReasonRequested = "RebootRequested"
	RebootReasonIssued    = "RebootIssued"
	RebootReasonSucceeded = "RebootSucceeded"
	RebootReasonFailed    = "RebootFailed"
)
```

この controller は `NodeRepair` gate が無効でも常に登録されます。実行中の reboot を、設定変更で中断させないためです。

```go: pkg/controllers/controllers.go
// The reboot controller only acts on NodeClaims with a committed reboot, so it always runs: a reboot already in flight
// finishes even if node repair is disabled or the provider stops selecting reboot.
```

### reboot の流れ

内部の動作は次のとおりです。

1. repair が `Rebooting=True/RebootRequested` を NodeClaim に付ける。
2. Node に taint `karpenter.sh/rebooting:NoSchedule` を付ける。drain で追い出された Pod が、同じノードに戻らないようにするためです。
3. drain する。`reboot-termination-grace-period` annotation で時間を区切れる。`0` なら強制的に drain します。未設定なら無制限です。
4. 実行前に、現在の boot ID を `karpenter.sh/reboot-pre-boot-id` annotation に保存する。boot ID が変われば、reboot 済みと判断して再実行しません。
5. cloud provider の `Reboot(ctx, nodeClaim, operationID)` を呼ぶ。受け付けられるまで、最大 5 分リトライします。
6. 新しい boot ID で Node が Ready になるのを、最大 20 分観察する。

`operationID` は、NodeClaim の UID、reboot の要求時刻、保存した boot ID から作られます。同じ reboot に対して `Reboot` が再度呼ばれても、cloud provider 側で冪等に扱えるようにするためです。

最小の drain 時間は 5 秒です。reboot が強制でも、直前に Pod がバインドされるのを拾うためです。

reboot が失敗した場合は、repair が置換に切り替えます。切り替え後の drain には上限が付きます（[#3407](https://github.com/kubernetes-sigs/karpenter/pull/3407)）。

## `--legacy-node-repair`

新しい repair では困る場合のために、旧実装に戻すフラグが追加されました（[#3400](https://github.com/kubernetes-sigs/karpenter/pull/3400)）。

```go: pkg/operator/options/options.go
fs.BoolVarWithEnv(&o.LegacyNodeRepair, "legacy-node-repair", "LEGACY_NODE_REPAIR", false, "When set with the NodeRepair feature gate, Karpenter runs the legacy node repair controller instead of node repair as a disruption method. The legacy controller only replaces nodes: it does not support terminate-first repair, reboot, repair policy priority or termination grace periods, or the karpenter.sh/do-not-repair annotation. NOTE: The legacy node repair controller is planned for deprecation. ...")
```

|項目|新実装（デフォルト）|`--legacy-node-repair`|
|--|--|--|
|実装|Disruption の Method|`node/legacyrepair` controller|
|budget|あり（reason は `Unhealthy`）|従来どおり|
|reboot|対応|非対応|
|terminate-first|対応|非対応|
|`do-not-repair`|対応|非対応|

旧実装は廃止予定と明記されています。使う場合は、新実装で困った理由を issue に書くよう案内されています。

:::message
`NodeRepair` を無効にしているクラスタは、この節の影響を受けません。有効にしている場合は、更新直後に挙動が変わります。budget に `Unhealthy` を指定していなければ、全 reason 共通の budget が repair にも適用される点に注意してください。
:::

# terminate-first

capacity が足りない NodePool では、Disruption の「先に置換ノードを起動してから、元のノードを消す」流れが成立しません。v1.15.0 では、先にノードを消して、後から Pod を再スケジュールする方式を選べます（RFC は [#3203](https://github.com/kubernetes-sigs/karpenter/pull/3203)）。

## どんなときに使うか

RFC では、次の 2 つが想定されています。

- **予約済みの容量（Capacity Reservation）の GPU フリート**: 予約が N 台分で、N 台すべて使っている。AMI を更新しても、N+1 台目を起動できないため、Drift が進まない。
- **上限に達した static NodePool**: `limits` で上限に達しており、置換用のノードを追加で起動できない。

ML 基盤で GPU を予約している場合、まさに当てはまる状況です。

## 2 つの gate

|Gate|対象|
|--|--|
|`TerminateFirstDrift`|Drift（[#3312](https://github.com/kubernetes-sigs/karpenter/pull/3312)）|
|`TerminateFirstRepair`|Repair（[#3342](https://github.com/kubernetes-sigs/karpenter/pull/3342)）。`NodeRepair` が必要|

どちらもデフォルトは無効です。

## 内部の動作

どちらの方式を使うかは、設定から自動で決まります。新しいフィールドや annotation はありません。

- **static NodePool**: ノード数が `spec.replicas` に達していれば terminate-first にします。
- **dynamic NodePool**: 候補のノードが消えたものとしてスケジューリングをシミュレーションします。置換先が、そのノードが占有していた予約の空きしかなければ、容量を増やせないと判断して terminate-first にします。他の選択肢（オンデマンドなど）があれば、従来どおり置換を先に行います。

terminate-first のコマンドは、置換ノードを持たない delete-only です。ノードを cordon して drain し、削除します。Pod が Pending になり、通常のプロビジョニングが空いた枠に置換ノードを起動します。

```go: pkg/controllers/disruption/types.go
// TerminateFirstDecision is a delete-only decision distinguished from DeleteDecision for terminate-first (RFC #3203).
TerminateFirstDecision Decision = "terminate-first"
```

安全性は、次の 2 つで保たれます。

- budget が、同時に消せる数を制限する。
- drain は PDB を守る。

起動の失敗（容量不足、AMI の不具合など）では、terminate-first に切り替わりません。RFC の Non-Goals に明記されています。構造的に容量が足りない場合だけが対象です。

## 関連する修正

- [#3398](https://github.com/kubernetes-sigs/karpenter/pull/3398): 予約が満杯のとき、static NodePool の repair と drift も terminate-first にする。
- [#3403](https://github.com/kubernetes-sigs/karpenter/pull/3403): static NodePool の InstanceType を解決できないとき、その NodePool だけをスキップする。以前は repair と drift の全体が止まっていました。
- [#3368](https://github.com/kubernetes-sigs/karpenter/pull/3368): static drift が上限で置換を用意できないとき、`DisruptionBlocked` event を出す。

## 新しいメトリクス

[#3404](https://github.com/kubernetes-sigs/karpenter/pull/3404) で、terminate-first の理由を示すラベル `terminate_first_reason` が追加されました。値は次の 2 つです。

|値|意味|
|--|--|
|`TerminateFirstNoReservedCapacity`|置換先が、ノードが占有していた満杯の予約の枠しかない|
|`TerminateFirstStaticAtLimit`|static NodePool が上限に達している|

また、Disruption の `decision` ラベルに、`terminate-first` と `reboot` の値が増えました。

# PodDeletionCostManagement

ReplicaSet の scale-down で、Karpenter が consolidate する予定のノード上の Pod から先に消えるようにする機能です。Alpha で、デフォルトは無効です（[#2894](https://github.com/kubernetes-sigs/karpenter/pull/2894)、RFC は [#2935](https://github.com/kubernetes-sigs/karpenter/pull/2935)）。

## 背景

Deployment の replica を減らすと、ReplicaSet controller がどの Pod を消すかを決めます。Karpenter が「このノードを consolidate したい」と考えていても、別のノードの Pod が消えると、consolidate が進みません。

ReplicaSet controller は、annotation `controller.kubernetes.io/pod-deletion-cost` の値が小さい Pod から先に消します。Karpenter がこの値を Pod に書けば、意図したノードから空けられます。

## 内部の動作

`pkg/controllers/pod/deletioncost` の controller が、1 分ごとに reconcile します。`cluster.ConsolidationState()` が前回から変わっていなければ、スキップします。

ノードは `RankNodes` で 3 つのグループに分けられます。

|グループ|対象|書き込む値|
|--|--|--|
|A|すでに disrupt 中（削除中）のノード|`math.MinInt32`（最優先で消える）|
|B/C|Drift 済み、通常のノード|`-n + i`（`n` は B/C の総数、`i` は 0 始まりの順位）|
|D|budget の外、対象外|annotation を削除|

B/C の中の順位は、Drift 済みが先で、次に通常のノード。それぞれ `SavingsRatio` の大きい順です。値が小さい Pod ほど先に消えるため、先頭のノードの Pod が最初に消えます。

実装の工夫を挙げます。

- **書き込みの上限**: 1 サイクルあたり最大 50 ノード分です。グループ A は上限の対象外で、すぐに書きます。
- **非同期**: 書き込みは `Queue` に積むだけで、完了を待ちません。
- **楽観ロック**: `MergeFromWithOptimisticLock` で書くため、他の書き込みと衝突したら次のサイクルで再試行します。
- **対象の Pod**: ReplicaSet 管理の Pod だけです。他の種類では、この annotation が使われないためです。
- **対象のノード**: Karpenter が管理するノードだけです。
- **予算の反映**: Drift と consolidation の budget を考慮し、実際に disrupt できる数に絞ってランクを付けます。

## `karpenter.sh/disruption-cost`

同じ PR で、`karpenter.sh/disruption-cost` annotation も追加されました。Pod を evict するコストをユーザーが指定するためのものです。値は int32 です。

|gate|Karpenter が読む annotation|
|--|--|
|無効|`karpenter.sh/disruption-cost`。なければ `controller.kubernetes.io/pod-deletion-cost`|
|有効|`karpenter.sh/disruption-cost` のみ|

gate を有効にすると、Karpenter が書いた `pod-deletion-cost` を、自分で disruption cost として読み返すことがなくなります。ユーザーが手で付けた `pod-deletion-cost` も読まれなくなる点に注意してください。

:::message
有効にすると、Pod への annotation の書き込みが増えます。kwok 用 Helm Chart の ClusterRole では、`pods` の verbs が `delete` から `delete`、`patch`、`update` に広がりました。あわせて `nodes/status` の `patch`、`services` の読み取り、VPA の読み取りも追加されています。自分の環境の Chart の ClusterRole に、同じ権限があるか確認してください。
:::

# API の変更

## `consolidateAfter` が必須ではなくなった

[#3220](https://github.com/kubernetes-sigs/karpenter/pull/3220) で、NodePool の `spec.disruption.consolidateAfter` にデフォルト値 `0s` が付き、必須ではなくなりました。

```go: pkg/apis/v1/nodepool.go
// +kubebuilder:default:="0s"
// +kubebuilder:validation:Pattern=`^(([0-9]+(s|m|h))+|Never)$`
// +kubebuilder:validation:Type="string"
// +kubebuilder:validation:Schemaless
// +optional
ConsolidateAfter NillableDuration `json:"consolidateAfter,omitempty"`
```

すでに値を指定している NodePool は、挙動が変わりません。省略した NodePool は、`0s` として扱われます。

## `Unhealthy` reason

NodePool の `disruption.budgets[].reasons` の enum に `Unhealthy` が追加されました。CRD を更新しないと、`Unhealthy` を指定した NodePool が apply できません。Helm Chart の CRD を、Controller と同じバージョンに更新してください。

## その他の CRD の差分

`NodeSelectorRequirement` の `operator` の enum が、`In`、`NotIn`、`Exists`、`DoesNotExist`、`Gt`、`Lt`、`Gte`、`Lte` の順に明示されました（[#2924](https://github.com/kubernetes-sigs/karpenter/pull/2924)）。受け付ける値は変わりません。並び順が変わっただけです。

# Scheduling の変更

## default topology spread の反映

[#3205](https://github.com/kubernetes-sigs/karpenter/pull/3205) で、kube-scheduler の `PodTopologySpread` の `defaultConstraints` を、Karpenter のスケジューリングのシミュレーションに反映できるようになりました（RFC は [#3183](https://github.com/kubernetes-sigs/karpenter/pull/3183)）。

### 背景

kube-scheduler は、`topologySpreadConstraints` を持たない Pod に、クラスタ共通の `defaultConstraints` を適用できます。一方、Karpenter は Pod の spec にある制約だけを見ます。たとえば、`DoNotSchedule` で zone を均等にする default があると、次のようなずれが起きます。

- スケジューラは、Pod を zone 間で分散しようとして、Pending にする。
- Karpenter は制約を知らず、同じ zone のノードしか用意しない。

### 設定方法

新しいフラグ `--scheduler-config`（環境変数 `SCHEDULER_CONFIG`）で、YAML か JSON を渡します。

```yaml: scheduler-config の例
podTopologySpread:
  defaultConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule
```

内部の動作は次のとおりです。

- 起動時に `yaml.UnmarshalStrict` で解析します。未知のフィールドがあると、起動に失敗します。
- 検証は kube-scheduler の `ValidatePodTopologySpreadArgs` と同じ規則です。`labelSelector` を持たせられません。同じ `topologyKey` と `whenUnsatisfiable` の重複もエラーです。
- 空文字なら、従来どおり何も変わりません。
- `labelSelector` は、kube-scheduler と同じ方法で Service や ReplicaSet などから導出されます。

Karpenter は kube-scheduler の実際の設定を読みません。設定を二重に管理することになるため、値は手で揃える必要があります。EKS のようなマネージドなコントロールプレーンでは、`defaultConstraints` をカスタマイズできるかどうかも確認が必要です。

## volume attach 上限

[#3202](https://github.com/kubernetes-sigs/karpenter/pull/3202) で、`InstanceType` に `VolumeAttachmentLimits` が追加されました。

```go: pkg/cloudprovider/types.go
// VolumeAttachmentLimits is the expected number of volumes that can be attached to nodes of this instance type, keyed by
// CSI driver name. Cloud providers that do not know a driver's limit ahead of time may omit it; limits reported
// by a node's CSINode take precedence once the node registers.
VolumeAttachmentLimits map[string]int
```

CSI ドライバごとの attach 上限です。ノードが登録された後は、`CSINode` の値が優先されます。provisioning のときに、まだ存在しないノードへ Pod を詰め込みすぎて、volume を attach できなくなるのを防げます。cloud provider がこの値を埋めるかどうかは、AWS Provider 側の対応次第です。

# Metrics の変更

## breaking change

更新前に確認が必要な変更が 2 つあります。

### `reason` ラベルの小文字化（[#3284](https://github.com/kubernetes-sigs/karpenter/pull/3284)）

次の 2 つのゲージで、`reason` ラベルの値が小文字になりました。

- `karpenter_nodepools_allowed_disruptions`
- `karpenter_nodepools_nodes_consuming_budgets`

```go: pkg/controllers/disruption/helpers.go
NodePoolAllowedDisruptions.Set(float64(allowedDisruptions), map[string]string{
	metrics.NodePoolLabel: nodePool.Name, metrics.ReasonLabel: strings.ToLower(string(reason)),
})
```

| |変更前|変更後|
|--|--|--|
|`reason`|`Drifted`、`Underutilized`、`Empty`|`drifted`、`underutilized`、`empty`、`unhealthy`|

`reason="Drifted"` のように大文字で絞っているクエリは、更新後に何も返さなくなります。

### `queue_failures_total` の `consolidation_type`（[#3294](https://github.com/kubernetes-sigs/karpenter/pull/3294)）

`karpenter_voluntary_disruption_queue_failures_total` の `consolidation_type` に、これまでは `decision` の値（`replace` など）が入っていました。v1.15.0 では、コマンドの consolidation type（`single`、`multi`、`empty`）が入ります。

```go: pkg/controllers/disruption/queue.go
DisruptionQueueFailuresTotal.Add(float64(len(failedLaunches)), map[string]string{
	decisionLabel:          string(cmd.Decision()),
	metrics.ReasonLabel:    strings.ToLower(string(cmd.Reason())),
	ConsolidationTypeLabel: cmd.ConsolidationType(),
})
```

## 追加と変更

|メトリクス|内容|
|--|--|
|`karpenter_pods_disruption_initiated_total`|Disruption で開始された Pod の disruption 数。再スケジュールが必要な Pod の数だけ増える。DaemonSet の Pod とミラー Pod は除く（[#3015](https://github.com/kubernetes-sigs/karpenter/pull/3015)）|
|Disruption の `decision` ラベル|`terminate-first`、`reboot` の値を追加|
|Disruption のメトリクス|`consolidation_policy` と `termination_mode` のラベルを追加（[#3179](https://github.com/kubernetes-sigs/karpenter/pull/3179)）|
|Balanced consolidation の `decision`|`approved` / `rejected` の値に分離（[#3322](https://github.com/kubernetes-sigs/karpenter/pull/3322)）|

`karpenter_pods_disruption_initiated_total` は、NodeClaim の disrupt にあわせて Pod 数を加算します。consolidation、repair、expiration、garbage collection のすべてが対象です。「どの理由で、何個の Pod を動かしたか」を集計できます。

```promql
sum by (reason) (increase(karpenter_pods_disruption_initiated_total[1h]))
```

メトリクスの dimension（ラベルとその値）は、コード上で `opmetrics.Label` と `opmetrics.Value` として定義され、説明つきでドキュメント化されるようになりました（[#3295](https://github.com/kubernetes-sigs/karpenter/pull/3295)）。

# 影響範囲とアップグレード時の確認事項

自分のクラスタに更新するとき、特に確認する項目を挙げます。GPU を使う学習・推論ワークロードや、予約済みの容量（Capacity Reservation）を使うクラスタでは、Node Repair と terminate-first の変更が効きやすいと考えています。

1. **`NodeRepair` を有効にしているか**: 有効なら、repair が budget の対象になり、挙動が変わります。budget の `reasons` に `Unhealthy` を指定するかを決めておきます。旧実装に戻すなら `--legacy-node-repair` です。
2. **CRD の更新**: `Unhealthy` reason を使うには、CRD を Controller と同じバージョンにそろえる必要があります。
3. **メトリクスのクエリ**: `reason` を大文字で絞っているダッシュボードやアラートがないか確認します。`queue_failures_total` の `consolidation_type` を使っている場合も同様です。
4. **Capacity Reservation の運用**: AMI 更新で Drift が止まっているなら、`TerminateFirstDrift` が使えるか検討します。有効にすると、置換の前にノードが消えるため、PDB と budget の設定が重要になります。
5. **ReplicaSet の scale-down**: `PodDeletionCostManagement` は Alpha です。使うなら、まずステージング環境で、RBAC と書き込みの量を確認します。
6. **kube-scheduler の default topology spread**: クラスタで `defaultConstraints` を使っているなら、`--scheduler-config` で Karpenter にも渡します。
7. **core を import している Provider**: `RepairPolicies` の action に `RebootNode` が加わります。Provider が reboot に対応する必要があります。

# まとめ

v1.15.0 は、Node Repair の仕組みを入れ替えたリリースです。repair が Disruption の Method になり、budget、優先順位、reboot、terminate-first を扱えるようになりました。あわせて、feature gate が 3 つ増えています。

自分のクラスタに適用する前に確認するのは、次の 3 点です。

- `NodeRepair` の有無と、`Unhealthy` の budget。
- メトリクスの `reason` ラベルの小文字化。
- Capacity Reservation を使う NodePool で、terminate-first が必要かどうか。

更新後は、`karpenter_pods_disruption_initiated_total` と `karpenter_nodepools_allowed_disruptions` で、挙動を確認する予定です。

なお本記事は、ソースの差分から読み取った内容で、実際のクラスタで更新した結果ではありません。公式の Upgrade Guide や AWS Provider 側の変更は別途確認してください。

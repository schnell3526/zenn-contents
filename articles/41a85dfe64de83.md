ML Platform Engineer として、普段から Karpenter を運用しています。管理しているクラスタで Karpenter を更新するにあたり、v1.5.0 で何が変わるかを調べました。

リリースノートだけでは挙動の変化を判断しにくい箇所があったため、ソースコード（`kubernetes-sigs/karpenter` の `v1.4.1..v1.5.0`）の差分を読みました。内部の動作を含めて、更新前に確認した内容をまとめます。

# 前提条件・環境

- 対象は `sigs.k8s.io/karpenter` のコアリポジトリです。
- v1.4.1 から v1.5.0 までの差分は 56 コミット、115 ファイルです。
- 半分以上はテスト移行（AWS Provider から core への E2E 移行）と依存更新です。
- 本記事では挙動に影響するものに絞ります。
- cloud provider（AWS Provider など）側の変更は読んでいません。

:::message
CRD のスキーマ変更はありません。`pkg/apis/crds/` の差分は `controller-gen` のバージョン注釈（v0.19.0 → v0.18.0）だけです。CRD の適用手順は従来どおりで問題ありません。
:::

# 変更点の全体像

|分類|変更|影響度|
|--|--|--|
|Disruption|Emptiness を Drift より先に評価|中|
|Disruption|Empty ノードの validation を専用化|中|
|Disruption|`karpenter_voluntary_disruption_failed_validations_total` を追加|低|
|Node 登録|`karpenter.sh/do-not-sync-taints` ラベルを追加|低（Provider 向け）|
|Scheduling|preferred nodeAffinity の validation を削除|中|
|Scheduling|`capacity-type` の値を実行時に検証|中|
|Scheduling|スケジューリングの並列化と `CPU_REQUESTS` オプションを追加|中|
|Metrics|`karpenter_pods_drained_total` を追加|低|
|Metrics|Pod の startup/bound 系メトリクスの削除漏れを修正|低|
|Perf|DaemonSet の watch を poll に変更、deepcopy の削減など|低|

# Disruption の変更

## Emptiness が Drift より先に評価される

[#2180](https://github.com/kubernetes-sigs/karpenter/pull/2180) で、`disruption.NewController` に渡す Method の順序が変わりました。

```go: pkg/controllers/disruption/controller.go
methods: []Method{
	// Delete any empty NodeClaims as there is zero cost in terms of disruption.
	NewEmptiness(c),
	// Terminate any NodeClaims that have drifted from provisioning specifications, allowing the pods to reschedule.
	NewDrift(kubeClient, cluster, provisioner, recorder),
	// Attempt to identify multiple NodeClaims that we can consolidate simultaneously to reduce pod churn
	NewMultiNodeConsolidation(c),
	// And finally fall back our single NodeClaim consolidation to further reduce cluster cost.
	NewSingleNodeConsolidation(c),
},
```

v1.4.1 では `Drift → Emptiness → Multi → Single` の順でした。v1.5.0 では `Emptiness → Drift → Multi → Single` です。Controller は先頭の Method から順に `disrupt()` を呼び、コマンドを実行できた時点でその reconcile を終えます。そのため先頭に置かれた Method ほど優先されます。

### Drift 側の内部動作の変化

v1.4.1 の `Drift.ComputeCommand` には、Drift 済みの候補の中から Pod のない（empty）ノードをまとめて削除する処理がありました。このとき消費される budget は、Drift 用の budget（`reasons: [Drifted]` など）でした。

v1.5.0 ではこの処理が逆になっています。

```go: pkg/controllers/disruption/drift.go
for _, candidate := range candidates {
	// Filter out empty candidates. If there was an empty node that wasn't consolidated before this, we should
	// assume that it was due to budgets. If we don't filter out budgets, users who set a budget for `empty`
	// can find their nodes disrupted here, which while that in itself isn't an issue for empty nodes, it could
	// constrain the `drift` budget.
	if len(candidate.reschedulablePods) == 0 {
		continue
	}
	...
}
```

Drift は empty の候補をスキップするようになりました。コメントのとおり、empty ノードが Emptiness で消えなかったのは budget が原因と見なし、Drift の budget を余計に消費しないようにしています。

### 運用への影響

- Drift（AMI 更新など）と empty ノードが同時にあるとき、empty ノードの削除が先に行われます。
- v1.4.1 では、Drift 済みの empty ノードは Drift の budget を使って消えていました。v1.5.0 では Emptiness の budget だけで判定されます。
- `reasons: [Empty]` の budget を `0` にしていると、Drift 済みの empty ノードも自動では消えなくなります。Drift の budget に空きがあっても同じです。

## Empty ノード専用の Validator

[#2220](https://github.com/kubernetes-sigs/karpenter/pull/2220) で validation が `Validator` interface になりました。

```go: pkg/controllers/disruption/validation.go
type Validator interface {
	Validate(context.Context, Command, time.Duration) (Command, error)
}
```

実装は 2 つあります。

- `EmptinessValidator`: Empty ノード用です。
- `ConsolidationValidator`: Multi / Single の Consolidation 用です。

v1.4.1 は `Validation` 構造体を 3 つの Method で共有し、`sync.Once` で最初の呼び出し時刻を記録していました。v1.5.0 ではこの共有状態がなくなり、Method ごとに Validator を持ちます。

### EmptinessValidator の処理

Empty ノードの validation は、[#2206](https://github.com/kubernetes-sigs/karpenter/pull/2206) で次の内容になりました。

1. `GetCandidates` で候補を取り直し、元の候補と突き合わせます（`mapCandidates`）。
2. `BuildDisruptionBudgetMapping` で budget を再計算します。
3. 候補ごとに、`IsNodeNominated` が true か、NodePool の残り budget が 0 なら除外します。
4. 残った候補だけで Command を作り直します。

```go: pkg/controllers/disruption/validation.go
if valid := lo.Filter(validatedCandidates, func(cn *Candidate, _ int) bool {
	if e.cluster.IsNodeNominated(cn.ProviderID()) || disruptionBudgetMapping[cn.NodePool.Name] == 0 {
		FailedValidationsTotal.Inc(map[string]string{ConsolidationTypeLabel: e.validationType})
		return false
	}
	disruptionBudgetMapping[cn.NodePool.Name]--
	return true
}); len(valid) > 0 {
	return valid, nil
}
```

v1.4.1 では、候補の 1 つでも Validation に失敗すると、Command 全体を破棄していました。v1.5.0 では有効な候補だけを残して実行します。複数の empty ノードをまとめて消すとき、1 台に Pod が nominate されたせいで全体が見送られる、という状況が減ります。タイトルの `non-churn empty nodes` はこの意味です。

Empty 判定ではスケジューリングのシミュレーションを行いません。`cluster.IsNodeNominated` を使うことで、Pod が載る予定のノードかどうかをメモリ上の状態だけで判断できます。

### ConsolidationValidator の処理

Multi / Single は従来の流れを引き継いでいます。

1. `consolidationTTL`（15 秒）待機します。
2. 候補を再取得して検証します。
3. `SimulateScheduling` で Command を再検証します。
4. 候補をもう一度検証します。

最後の再検証は、issue [#1167](https://github.com/kubernetes-sigs/karpenter/issues/1167) の race 対策です。

## 失敗した validation の新メトリクス

[#2239](https://github.com/kubernetes-sigs/karpenter/pull/2239) で `karpenter_voluntary_disruption_failed_validations_total` が追加されました。

```go: pkg/controllers/disruption/metrics.go
FailedValidationsTotal = opmetrics.NewPrometheusCounter(
	crmetrics.Registry,
	prometheus.CounterOpts{
		Namespace: metrics.Namespace,
		Subsystem: voluntaryDisruptionSubsystem,
		Name:      "failed_validations_total",
		Help:      "Number of candidates that were selected for disruption but failed validation. Labeled by consolidation type.",
	},
	[]string{ConsolidationTypeLabel},
)
```

ラベルは `consolidation_type` で、値は `empty` / `multi` / `single` です。選ばれた候補が validation で落とされた数を見られます。Pod の nominate や budget の変化が原因です。「Consolidation が進まない」ときの調査に使えます。

# Node 登録の変更

## `karpenter.sh/do-not-sync-taints` ラベル

[#2125](https://github.com/kubernetes-sigs/karpenter/pull/2125) で、Node ラベル `karpenter.sh/do-not-sync-taints: "true"` が追加されました。Node の登録処理（`Registration.syncNode`）は、このラベルがあると NodeClaim の taint を Node に同期しません。

```go: pkg/controllers/nodeclaim/lifecycle/registration.go
// We do not sync the taints if this label is present. We instead assume that the karpenter provider
// is managing taints. We still manage/remove the unregistered taint to signal the end of syncing.
if value, ok := node.Labels[v1.NodeDoNotSyncTaintsLabelKey]; !ok || value != "true" {
	// Sync all taints inside NodeClaim into the Node taints
	node.Spec.Taints = scheduling.Taints(node.Spec.Taints).Merge(nodeClaim.Spec.Taints)
	node.Spec.Taints = scheduling.Taints(node.Spec.Taints).Merge(nodeClaim.Spec.StartupTaints)
}
```

ポイントは次のとおりです。

- 同期をやめるのは `spec.taints` と `spec.startupTaints` の Merge だけです。
- `karpenter.sh/unregistered` taint の削除は、ラベルがあっても必ず行われます。登録完了のシグナルだからです。
- Node ラベルは `lo.Assign(node.Labels, nodeClaim.Labels, {registered: "true"})` で同期されます。ラベルの同期は止まりません。
- 値は文字列の `"true"` のみ有効です。

主な用途は、cloud provider や kubelet が独自に taint を管理している環境です。通常の EKS 利用者が設定する場面は多くありません。

# Scheduling の変更

## preferred nodeAffinity の validation 削除

[#2182](https://github.com/kubernetes-sigs/karpenter/pull/2182) で、`validateAffinity` から `PreferredDuringSchedulingIgnoredDuringExecution` の検証が削除されました。

```go: pkg/controllers/provisioning/provisioner.go
func validateAffinity(ctx context.Context, p *corev1.Pod) (errs error) {
	if p.Spec.Affinity == nil {
		return nil
	}
	if p.Spec.Affinity.NodeAffinity != nil {
		if p.Spec.Affinity.NodeAffinity.RequiredDuringSchedulingIgnoredDuringExecution != nil {
			for _, term := range p.Spec.Affinity.NodeAffinity.RequiredDuringSchedulingIgnoredDuringExecution.NodeSelectorTerms {
				errs = multierr.Append(errs, validateNodeSelectorTerm(ctx, term))
			}
		}
	}
	return errs
}
```

`GetPendingPods` は、validation に失敗した Pod を「無視する Pod」として扱い、provisioning の対象から外します。v1.4.1 では preferred 側に Karpenter が扱えない要件があると、Pod 全体が無視されていました。preferred は「満たせなくてもよい」条件です。それでノード作成が止まるのは意図に反するため、v1.5.0 では検証を外しています。

この修正で、preferred nodeAffinity に未対応の matchExpressions や制限ラベルを含む Pod でも、provisioning の対象になります。preferred 条件は、従来どおり Preferences の relax 機構で満たせなければ緩和されます。

## `capacity-type` の値を実行時に検証

[#2164](https://github.com/kubernetes-sigs/karpenter/pull/2164) で `WellKnownValuesForRequirements` が追加され、`karpenter.sh/capacity-type` に指定できる値が検証されるようになりました。

```go: pkg/apis/v1/labels.go
WellKnownValuesForRequirements = map[string]sets.Set[string]{
	CapacityTypeLabelKey: sets.New(
		CapacityTypeOnDemand,
		CapacityTypeSpot,
		CapacityTypeReserved,
	),
}
```

`ValidateRequirement` から呼ばれる `validateWellKnownValues` は、`In` 演算子の requirement だけを対象に次のように振る舞います。

|状態|結果|
|--|--|
|有効な値が 1 つもない|エラー（NodePool が Ready にならない）|
|`minValues` に対して有効な値が足りない|エラー（NodePool が Ready にならない）|
|有効な値と無効な値が混在|エラーログを出して、有効な値だけで続行|

たとえば `capacity-type In [spot, on_demand]` のようなタイプミスは、`on_demand` だけが無効値として扱われます。`spot` は有効なので NodePool は Ready のままで、ログにだけエラーが出ます。`In [on_demand]` のように全て無効だと、NodePool は Ready になりません。

:::message alert
アップグレード前に、既存の NodePool の `capacity-type` の値を確認してください。無効値だけを指定していた NodePool は、v1.5.0 で Ready にならなくなります。
:::

また、`ValidateRequirement` と `RuntimeValidate` の引数に `ctx` が追加されました。Karpenter を import して使う cloud provider 側では、コンパイルエラーになります。

## スケジューリングの並列化と `CPU_REQUESTS`

[#2126](https://github.com/kubernetes-sigs/karpenter/pull/2126) で、Pod を既存ノード・in-flight の NodeClaim に載せられるか調べる処理が並列化されました。

### 並列度の決め方

並列度は新オプション `CPU_REQUESTS`（`--cpu-requests`）から決まります。

```go: pkg/controllers/provisioning/provisioner.go
opts := []scheduler.Options{
	scheduler.DisableReservedCapacityFallback,
	scheduler.NumConcurrentReconciles(int(math.Ceil(float64(options.FromContext(ctx).CPURequests) / 1000.0))),
}
```

`CPU_REQUESTS` は Controller コンテナの CPU requests をミリコア単位で受け取ります。1000m ごとに 1 ワーカーで、既定値は `1000`（= 1 ワーカー）です。0 以下を指定すると起動に失敗します。

core リポジトリの kwok 用 Helm Chart は、Downward API の `resourceFieldRef` で渡しています。

```yaml: kwok/charts/templates/deployment.yaml
- name: CPU_REQUESTS
  valueFrom:
    resourceFieldRef:
      containerName: controller
      divisor: 1m
      resource: requests.cpu
```

AWS Provider の Helm Chart が同様に設定しているかは、この調査では確認していません。使っている Chart のバージョンで `CPU_REQUESTS` が渡されているかを確認してください。渡されていなければ 1 ワーカーのままで、従来と同じ直列の動作になります。

### 並列処理の実装

`addToExistingNode` と `addToInflightNode` は、`parallelizeUntil` で候補ごとの `CanAdd` を並列に呼びます。

```go: pkg/controllers/provisioning/scheduling/scheduler.go
parallelizeUntil(s.numConcurrentReconciles, len(s.existingNodes), func(i int) bool {
	r, err := s.existingNodes[i].CanAdd(pod, s.cachedPodData[pod.UID], volumes)
	if err == nil {
		mu.Lock()
		defer mu.Unlock()

		// Ensure that we always take an earlier successful schedule to keep consistent ordering
		if i >= idx {
			return false
		}
		existingNode = s.existingNodes[i]
		requirements = r
		idx = i
		return false
	}
	return true
})
```

仕組みは次のとおりです。

- `CanAdd` は副作用のない判定だけを行います。Pod の追加は、勝者が決まってから `Add` で行います。
- 複数のワーカーが成功しても、最小の index を採用します。並列化しても、直列実行と同じ結果になります。
- 成功したワーカーは `false` を返して終了します。
- PV のボリューム取得（`GetVolumes`）は、並列化の前に 1 回だけ行います。

大規模クラスタで Pod が大量に Pending のとき、スケジューリングのシミュレーションが速くなります。

## その他の Scheduling 向け最適化

- [#2224](https://github.com/kubernetes-sigs/karpenter/pull/2224): ExistingNode が持つ値を「消費した requests」から「残りの resources」に変えました。`resources.SubtractFrom` で in-place に引くため、Pod ごとの `Merge` による alloc がなくなります。
- [#2241](https://github.com/kubernetes-sigs/karpenter/pull/2241): `n.Available()` の呼び出しを 1 回にしました。
- [#2250](https://github.com/kubernetes-sigs/karpenter/pull/2250): `OrderByPrice` で、`Offerings.Available().Compatible(reqs)` が作る中間スライスをやめ、ループで最小価格を探します。

:::message
[#2250](https://github.com/kubernetes-sigs/karpenter/pull/2250) では、同価格のときの `Name` による比較（`its[i].Name < its[j].Name`）も削除されています。同価格の InstanceType の並び順は、`sort.Slice` の実装に依存するようになりました。
:::

# Metrics の変更

## `karpenter_pods_drained_total`

[#2044](https://github.com/kubernetes-sigs/karpenter/pull/2044) で、ノードの終了時にドレインされた Pod 数を数えるカウンタが追加されました。

```go: pkg/controllers/node/termination/terminator/eviction.go
reason := evictionReason(ctx, key, q.kubeClient)
q.recorder.Publish(terminatorevents.EvictPod(&corev1.Pod{ObjectMeta: metav1.ObjectMeta{Name: key.Name, Namespace: key.Namespace}}, reason))
PodsDrainedTotal.Inc(map[string]string{ReasonLabel: reason})
```

Eviction API が成功したときに、`reason` ラベル付きで加算されます。`reason` は Eviction イベントに載る理由と同じです。NodeClaim の `DisruptionReason` condition が true ならその Reason（`Drifted`、`Underutilized` など）、そうでなければ `Forceful Termination` です。NodeClaim が見つからないときは空文字になります。「どの理由で何個の Pod を退避したか」を PromQL で集計できます。

```promql
sum by (reason) (increase(karpenter_pods_drained_total[1h]))
```

## Pod の startup / bound メトリクスの修正

[#2146](https://github.com/kubernetes-sigs/karpenter/pull/2146) と [#2147](https://github.com/kubernetes-sigs/karpenter/pull/2147) で、メトリクスが残り続ける問題が直りました。

- [#2147](https://github.com/kubernetes-sigs/karpenter/pull/2147): すでに Node にバインド済み（`PodScheduled=True`）の Pod は、`karpenter_pods_scheduling_undecided_time_seconds` を削除します。
- [#2146](https://github.com/kubernetes-sigs/karpenter/pull/2146): Pod が Pending のまま、`schedulable` の時刻が 0 になると、`karpenter_pods_provisioning_unstarted_time_seconds` と `unbound_time_seconds` を idempotent に削除します。
- `Cluster.MarkPodSchedulingDecisions` のシグネチャが `(ctx, podErrors, nodePoolToPods)` に変わりました。エラーのある Pod は `podsSchedulableTimes` と `podHealthyNodePoolScheduledTime` から削除されます。
- `NodePoolToPodMapping()` が `Results` に追加され、NodePool ごとの Pod 一覧を 1 回で取れます。

# 内部のパフォーマンス改善

|PR|内容|
|--|--|
|[#2226](https://github.com/kubernetes-sigs/karpenter/pull/2226)|DaemonSet の controller は、Update / Delete のイベントを無視し、Create のみ受け取る。`RequeueAfter: time.Minute` で 1 分ごとに再取得|
|[#2232](https://github.com/kubernetes-sigs/karpenter/pull/2232)|NodeClaim の watch ハンドラ内の deepcopy を削除|
|[#2233](https://github.com/kubernetes-sigs/karpenter/pull/2233)|`GetCandidates` での Node の deepcopy を 1 回にする|
|[#2247](https://github.com/kubernetes-sigs/karpenter/pull/2247)|Node Health controller で NodePool / Cluster の健全性判定時の deepcopy を削減|

DaemonSet は Update が多く、そのたびにクラスタ状態の再計算が走っていました。DaemonSet の spec 変更は 1 分以内の poll で反映されるため、大規模クラスタでの負荷が下がります。反映が最大 1 分遅れる点は、挙動の違いとして覚えておくとよいです。

# 影響範囲とアップグレード時の確認事項

自分のクラスタに更新するとき、特に確認する項目を挙げます。GPU を使う学習・推論ワークロードや、バッチジョブのように Pod の入れ替わりが多いクラスタでは、Disruption と Scheduling の変更が効きやすいと考えています。

1. **NodePool の `capacity-type`**: 無効な値だけの NodePool がないか確認します。
2. **Drift と Empty の budget**: `reasons` ごとに budget を分けている場合、Emptiness の優先化で削除順が変わります。
3. **Helm Chart の `CPU_REQUESTS`**: 並列スケジューリングを使うには、Controller の CPU requests が環境変数で渡される必要があります。
4. **メトリクスの監視**: `karpenter_voluntary_disruption_failed_validations_total` と `karpenter_pods_drained_total` が追加されます。
5. **core を import している Provider**: `ValidateRequirement(ctx, ...)` と `RuntimeValidate(ctx)` のシグネチャ変更に対応が必要です。

# まとめ

v1.5.0 は新機能よりも、Disruption の優先順位と validation の整理、スケジューリングの並列化が中心のリリースです。自分のクラスタに適用する前に確認するのは、`capacity-type` の検証と Emptiness の優先化の 2 点です。更新後は、追加された 2 つのメトリクスで挙動を確認する予定です。

なお本記事は、ソースの差分から読み取った内容で、実際のクラスタで更新した結果ではありません。公式の Upgrade Guide や AWS Provider 側の変更は別途確認してください。

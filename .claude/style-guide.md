技術記事スタイルガイド
===

# 基本構成

## 記事の構造

```markdown
---
title: "【カテゴリ】具体的で分かりやすいタイトル"
emoji: "📊"
type: "tech" # tech: 技術記事 / idea: アイデア
topics: ["topic1", "topic2", "topic3"]
published: false
---

:::message alert
重要な注意事項がある場合はここに記載
:::

導入文（1-2文で記事の目的を簡潔に説明）

# 前提条件・環境

# メインコンテンツ

## サブセクション

### 詳細説明

# まとめ（必要に応じて）
```

## 見出しのルール

- 必ず `#` (H1) から開始
- 階層は順番に深くする（# → ## → ### の順）
- 見出しは簡潔で具体的に
- 見出しの前後は1行空ける

# 文体・表現

## 基本的な文体

- です・ます調で統一
- 簡潔で分かりやすい説明を心がける
- 冗長な表現は避ける
- 技術的内容は端的に説明
- 英単語と日本語の間にはスペースを入れる（例: `GitHub Actions で Terraform` ）

## 文章重視の執筆スタイル

技術記事では、過度に構造化（表やリスト）するよりも、**文章での説明を重視**します。

### 基本方針

- 表やリストは最小限にとどめる
- 概念や仕組みは文章で丁寧に説明する
- 箇条書きで済ませず、文脈を持った説明を心がける
- 読者が理解しやすい流れを意識する

### 良い例と悪い例

```markdown
<!-- NG: 過度に構造化 -->
## OpenTelemetry のコンポーネント

| コンポーネント | 説明 |
|--------------|------|
| SDK | アプリケーションに組み込むライブラリ |
| Collector | データ収集・処理 |
| Exporter | バックエンド送信 |

<!-- OK: 文章で説明 -->
## OpenTelemetry のアーキテクチャ

OpenTelemetry を使ったトレーシングシステムは、以下の 3 つのコンポーネントで構成されます。

**SDK (Software Development Kit)** は、アプリケーションに組み込むライブラリです。トレースやスパンを生成し、コンテキストを伝播させる役割を担います。各プログラミング言語（Python、Go、Java など）に対応した SDK が提供されています。

**Collector (コレクター)** は、テレメトリデータを受け取り、処理し、バックエンドにエクスポートするコンポーネントです。データのフィルタリング、サンプリング、バッチ処理などを行います。Collector を挟むことで、アプリケーションとバックエンドを疎結合に保てます。

**Exporter (エクスポーター)** は、データを特定のバックエンド（Jaeger、Zipkin、Prometheus など）に送信する機能です。OpenTelemetry Protocol (OTLP) という標準プロトコルを使うことで、複数のバックエンドに対応できます。
```

### 表を使うべき場面

以下の場合は、表を使った方が適切です。

- ポートやコマンドの対応表など、データが明確に対応関係にある場合
- 比較表（A vs B）
- スペックや設定値の一覧

```markdown
<!-- 表が適切な例 -->
| サービス     | URL                    | ユーザー名 | パスワード |
| ------------ | ---------------------- | ---------- | ---------- |
| Grafana      | http://localhost:30001 | admin      | admin      |
| Prometheus   | http://localhost:30000 | -          | -          |
```

### 箇条書きを使うべき場面

以下の場合は、箇条書きが適切です。

- 前提条件や要件の列挙
- 手順の列挙（順序がある場合は番号付きリスト）
- 単純な項目の列挙

```markdown
<!-- 箇条書きが適切な例 -->
# 前提条件・環境

本記事では、以下の環境を前提としています。

- Docker がインストールされていること
- Kind がインストールされていること
- kubectl がインストールされていること
```

## 導入部分

```markdown
# 良い例
Kind を使って簡単なリソースモニタリング環境を構築します。

研究室で用いている共用計算資源の管理のメモ書きです。

# 避けるべき例
この記事では〜について説明していきたいと思います。（冗長）
```

## リストの使い方

```markdown
# 前提条件（箇条書き）
- Docker がインストールされていること
- Kind がインストールされていること

# 手順（番号付きリスト）
1. Kind クラスタの作成
2. metrics-server のデプロイ
3. 動作確認
```

# コードブロック

## 基本ルール

- 必ず言語を指定（```bash, ```python など）
- ファイル名があれば記載（```bash: setup.sh）
- コマンド実行結果は別ブロックで記載
- 長いコードは適度にコメントを追加

```markdown
```bash
# 環境変数の設定
export GCC_VERSION=11.2.0

# ビルド実行（-jオプションで並列化）
make -j`nproc` > /dev/null
```
```

# 特殊記法

## メッセージブロック

```markdown
:::message
通常のメッセージ
:::

:::message alert
重要な警告メッセージ
:::
```

## 詳細情報の折りたたみ

```markdown
:::details インストールでエラーが出る場合
詳細なトラブルシューティング内容
:::
```

## 表形式

```markdown
|コマンド|説明|
|--|--|
|`x`|カーソル位置の1文字を削除|
|`dd`|1行を切り取り|
```

# 避けるべきパターン

## コロン直後の改行

```markdown
<!-- NG -->
何かの項目:
- 値1
- 値2

<!-- OK -->
何かの項目: 値1, 値2

<!-- OK（別の表現）-->
何かの項目は以下のとおりです。
- 値1
- 値2
```

## 冗長な表現

```markdown
<!-- NG -->
〜について説明していきたいと思います
〜ということになります
〜ではないでしょうか

<!-- OK -->
〜を説明します
〜になります
〜です
```
